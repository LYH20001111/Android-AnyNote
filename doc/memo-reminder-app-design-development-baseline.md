# 随记应用｜设计与开发基线

> 版本：v0.1
> 
> 状态：产品需求基线（MVP 可开发）
> 
> 目标：将目前已经确认的产品选择，整理成可以直接用于产品设计、UI 设计、技术设计和开发拆解的统一基线。

---

## 1. 产品概述

### 1.1 产品定位

这是一个 **以“在正确的时间把用户写下的内容主动送到用户眼前”为核心能力的个人备忘录/提醒应用**。

核心不是单纯记录内容，而是：

> 用户记录一件事情 → 设置一个或多个提醒规则 → 到时间由手机系统发出提醒 → 用户可以直接完成、稍后提醒，或进入 App 处理 → 所有执行结果进入历史记录。

### 1.2 核心原则

1. **提醒优先**：提醒是产品核心能力，不能依赖 App 一直运行在前台或后台。
2. **本地优先**：MVP 以本地数据和本地提醒为主，不要求登录和服务器。
3. **规则与事件分离**：提醒规则负责描述“什么时候提醒”，提醒事件负责记录“这一次是否真的发生、是否完成”。
4. **系统通知是执行层，不是数据源**：App 本地数据库是唯一事实来源；系统里的待提醒任务可以被重新同步/重建。
5. **内容可直接看到**：通知默认尽可能显示备忘录内容，但每条备忘录可单独关闭通知正文预览。
6. **重复提醒可持续管理**：重复规则、跳过某次、稍后提醒、完成某次与结束整个重复系列必须互不混淆。

# 3. 核心对象模型

整个产品建议从以下数据关系开始设计：

```text
分类 Folder
   │
   └── 备忘录 Note
          │
          ├── 内容 Content
          │      ├── 文字
          │      ├── 图片
          │      ├── 文件
          │      └── 语音
          │
          ├── 0..N 提醒规则 ReminderRule
          │       └── 每条规则定义一次性/重复时间规则
          │
          └── 0..N 提醒事件 ReminderOccurrence
                  └── 记录每一次计划提醒的实际执行状态
```

## 3.1 Note（备忘录）

建议字段：

- `id`
- `folder_id`
- `title`（可空）
- `body`
- `priority`：low / medium / high
- `status`：active / completed / trashed
- `notification_preview_enabled`
- `created_at`
- `updated_at`
- `completed_at`
- `deleted_at`

## 3.2 Attachment（附件）

建议字段：

- `id`
- `note_id`
- `type`：image / file / audio
- `local_path`
- `file_name`
- `mime_type`
- `size`
- `created_at`

MVP 中附件建议全部保存在本机应用私有存储中。

## 3.3 ReminderRule（提醒规则）

建议字段：

- `id`
- `note_id`
- `type`：once / daily / weekly / monthly / yearly / weekdays / custom_weekdays / interval
- `start_datetime`
- `time_of_day`
- `timezone`
- `interval_value`
- `interval_unit`：day / week / month / year
- `weekdays`
- `day_of_month`
- `month_of_year`
- `end_date`
- `completion_mode`
- `auto_repeat_enabled`
- `auto_repeat_interval`
- `auto_repeat_limit`（预留）
- `is_enabled`
- `created_at`
- `updated_at`

## 3.4 ReminderOccurrence（提醒事件）

这是本产品非常重要的对象。

建议字段：

- `id`
- `reminder_rule_id`
- `note_id`
- `scheduled_at`
- `triggered_at`
- `completed_at`
- `status`
- `snoozed_until`
- `skipped_at`
- `notification_id`
- `created_at`
- `updated_at`

建议状态：

```text
scheduled      待提醒
triggered      已触发
snoozed        已稍后提醒
completed      已完成
skipped        已跳过本次
expired        已过期但未完成
cancelled      已取消
```

# 5. 提醒规则设计

## 5.1 一条备忘录支持多个提醒

一个 Note 可拥有多个 ReminderRule。

例如：

```text
备忘录：准备去旅行

提醒 1：2026/10/01 10:00
提醒 2：2026/10/15 10:00
提醒 3：2026/10/30 18:00
```

这些提醒彼此独立，可以分别编辑、停用、删除。

---

## 5.2 一次性提醒

支持：

- 年
- 月
- 日
- 时
- 分
- 秒

例如：

```text
2026/10/25 18:32:45
```

产品 UI 默认以“分钟级”为主要展示精度，但数据模型必须保存秒。

---

## 5.3 重复提醒

支持以下规则：

### 每天

```text
每天 09:00
```

### 每周

```text
每周一 09:00
```

### 每月

```text
每月 15 日 09:00
```

### 每年

```text
每年 10 月 15 日 09:00
```

### 工作日

```text
周一至周五 09:00
```

### 自定义星期

例如：

```text
周一、周三、周五 18:30
```

### 每 N 天

例如：

```text
每 3 天 09:00
```

### 每 N 周

例如：

```text
每 2 周，周一 09:00
```

### 每 N 月

例如：

```text
每 3 个月，15 日 09:00
```

### 每 N 年

例如：

```text
每 2 年，10 月 15 日 09:00
```

# 6. 重复规则的业务边界

## 6.1 结束日期

重复提醒支持“结束日期”。

开发基线处理：

- 用户可以设置结束日期。
- 如果界面允许不填写结束日期，则表示持续重复；这是为了避免产品出现“重复功能却必须填结束日期”的不合理体验。
- 一旦到达结束日期，规则自动结束，不再产生新的 ReminderOccurrence。

## 6.2 每月不存在日期

用户设置：

```text
每月 31 日 20:00
```

当月份没有 31 日时：

> 自动使用当月最后一天。

例如：

```text
2月31日 → 2月28日 / 29日
4月31日 → 4月30日
```

必须统一由日期规则引擎处理，不能在 UI 层临时判断。

## 6.3 闰年

例如：

```text
每年 2 月 29 日
```

建议沿用同一原则：不存在该日期的年份跳过该次；如产品未来需要“最后一天”等特殊规则，再单独加入配置。

## 6.4 跳过某一次

例如：

```text
每周一 09:00
```

用户可以：

> 跳过本次

结果：

```text
本次 skipped
下一周继续 scheduled
```

不能修改整个重复规则。

# 7. 完成逻辑

## 7.1 一次性提醒

用户可根据该备忘录的“完成设置”决定：

### 不使用完成状态

提醒触发后，本次提醒事件结束。

### 使用完成状态

提醒触发后变为“待处理”，用户可以完成。

---

## 7.2 重复提醒

创建重复提醒时，提供：

```text
完成方式

○ 完成本次，后续继续提醒
○ 完成后结束整个重复提醒
```

开发默认推荐第一项作为默认值，但不能删除第二项能力。

---

# 8. 自动重复提醒

用户可以对“未完成提醒”开启自动重复，例如：

```text
原定提醒：10:00
自动重复：每 10 分钟
```

效果：

```text
10:00 第一次提醒
10:10 再次提醒
10:20 再次提醒
……
```

自动重复与原始周期规则是两个不同概念：

```text
重复规则：每周一 10:00
自动重复：每 10 分钟提醒一次
```

其中自动重复只针对当前 ReminderOccurrence，不改变“每周一”的长期规则。

开发时必须避免出现“自动重复把下一周规则也推进了”的 Bug。

---

# 9. 稍后提醒 Snooze

通知到达后，用户可直接操作：

```text
完成
稍后提醒
```

“稍后提醒”支持：

```text
10 分钟后
30 分钟后
1 小时后
自定义时间
```

## 9.1 Snooze 的原则

Snooze 只修改当前提醒事件：

```text
原始计划：09:00
Snooze：30分钟
新的执行：09:30
```

不会把重复规则改成：

```text
以后每周都 09:30
```

### 完成后的处理

用户在 09:30 点击完成：

> 当前事件 completed。

原来的长期重复规则继续照常产生下一次提醒。

# 10. 通知设计

## 10.1 通知目标

用户不打开 App，也应该可以通过系统通知看到提醒内容。

通知包含：

```text
标题
正文
```

当用户未设置自定义标题时，可以使用：

```text
提醒
```

正文使用备忘录主内容摘要/完整内容。

---

## 10.2 通知展示

需要支持：

- 横幅
- 锁屏
- 通知中心/通知栏
- 声音
- App 角标

不做全屏式提醒。

## 10.3 通知正文隐私

每条备忘录独立控制：

```text
在通知中显示内容：开启 / 关闭
```

关闭时，通知可显示：

```text
提醒
你有一个新的提醒
```

开启时：

```text
提醒
明天下午去银行办理银行卡，记得带身份证。
```

注意：最终锁屏是否显示完整预览，还受操作系统和用户系统设置影响，因此产品不能承诺“所有情况下都一定显示全文”。

# 11. 通知快捷操作

为了让产品核心体验成立，通知建议支持直接操作：

```text
[完成]
[稍后提醒]
```

“稍后提醒”可以进入预设选项，必要时再进入自定义时间界面。

iOS 原生通知支持通过通知类别和动作定义可交互按钮；横幅等展示位置对可见操作数量存在系统限制，因此 UI 需要以系统能力为准设计。citeturn412811search0turn412811search7

Android 端实现等价能力时，需要使用系统通知动作，并针对不同 Android 版本进行兼容测试。

# 14. 历史记录

历史不是简单的“删除列表”，而是产品的重要数据资产。

例如：

```text
提交周报
每周一 09:00

2026/09/14 09:00
已提醒
09:18 已完成

2026/09/07 09:00
已提醒
09:06 已完成
```

历史必须至少能看到：

- 计划提醒时间
- 实际触发时间
- 是否完成
- 完成时间
- 是否跳过
- 是否由稍后提醒导致重新触发

建议支持时间范围筛选和搜索。

# 15. 完成后的数据流

当一个提醒事件完成：

```text
ReminderOccurrence
      ↓
   completed
      ↓
当前活动列表移除
      ↓
历史记录保留
```

对于重复规则：

```text
当前事件 completed
      ↓
根据 ReminderRule 计算下一次 occurrence
      ↓
继续等待下一次提醒
```

只有用户选择“完成后结束整个重复提醒”时，才：

```text
当前事件 completed
      ↓
ReminderRule disabled/completed
      ↓
不再产生后续事件
```

---

# 16. 删除与回收站

用户删除备忘录：

```text
Active
  ↓
Trash
```

回收站中：

- 不再产生提醒
- 系统通知全部取消
- 数据暂不物理删除
- 用户可以恢复
- 用户可以永久删除

回收站不自动清空。

恢复后：

```text
Trash
 ↓
Active
 ↓
重新计算并注册未来提醒
```

永久删除时：

- 删除 Note
- 删除 ReminderRule
- 删除未来通知
- 删除附件
- 删除关联的历史记录（建议明确告知用户这是不可逆操作）

# 21. 权限与系统依赖

这是本产品最重要的技术注意事项之一。

## 21.1 iOS

iOS 支持本地通知，系统可以在 App 不运行或处于后台时负责通知的交付；本地通知可以配置标题、正文、声音、角标和基于日历/时间的触发条件。citeturn673747search1turn673747search12

但用户必须允许通知。若用户拒绝通知，系统不会正常向该 App 交付通知，App 必须检测权限状态并给出设置引导。citeturn673747search6

因此 App 启动时、保存提醒时、进入设置时，都应该检查通知授权状态。

另外，通知预览是否显示完整内容还受到用户系统设置影响，所以应用只能控制自身希望发送什么内容，不能完全控制锁屏最终展示策略。citeturn673747search8turn673747search9

## 21.2 Android

Android 13（API 33）及以上需要处理 `POST_NOTIFICATIONS` 通知运行时权限；用户拒绝后，普通通知将无法正常发布。citeturn412811search4turn412811search6

如果产品要求非常精确的提醒时间，Android 端需要评估并正确使用 exact alarm 机制。Android 14 开始，新安装的多数目标版本较新的应用不会默认获得 `SCHEDULE_EXACT_ALARM`，该权限需要按平台规则处理。citeturn673747search0turn673747search7

因此：

> “用户可以把时间设置到秒” ≠ “应用可以保证所有设备在精确到毫秒的同一时刻响起”。

产品文案应承诺“提醒时间支持精确到秒”，而不是“绝对零误差、100% 到秒必达”。

## 21.3 不做全屏提醒

本产品明确不采用全屏式提醒，因此可以避免将普通备忘录提醒包装成闹钟类体验，也减少相应的平台限制和审核风险。Android 14 对 full-screen intent 的适用范围有更严格的限制。citeturn673747search5

# 22. 通知调度的技术架构原则

不要设计成：

```text
App 后台一直运行
      ↓
App 自己每秒检查时间
      ↓
到了时间再发送通知
```

这种思路不可靠，也不符合移动系统后台运行模型。

应该设计成：

```text
本地数据库
    ↓
提醒规则引擎
    ↓
计算未来需要触发的时间点
    ↓
注册给操作系统
    ↓
由系统负责到点触达
```

App 被关闭、进入后台后，提醒任务仍应依靠系统调度机制执行。

当 App 再次启动时：

```text
读取数据库
    ↓
检查系统实际已注册的提醒
    ↓
发现缺失/失效
    ↓
重新调度未来提醒
```

# 23. 修改提醒时的强制规则

用户修改：

- 内容
- 标题
- 提醒时间
- 重复规则
- 是否显示通知正文
- 完成模式
- 分类

都可能影响系统已注册的通知。

统一流程建议：

```text
修改 Note / ReminderRule
        ↓
取消旧的系统通知
        ↓
更新本地数据库
        ↓
重新计算未来事件
        ↓
注册新的系统通知
```

禁止只更新数据库而不更新系统通知。

# 24. App 被强制关闭、系统重启后的处理

必须设计“恢复调度”机制。

典型流程：

```text
设备重启 / 权限改变 / App 再次启动
            ↓
读取本地 ReminderRule
            ↓
计算未来提醒
            ↓
重新注册必要通知
```

尤其需要测试：

- 手机重启
- App 被系统结束
- App 被用户从任务列表划掉
- 用户修改系统时间
- 用户修改时区
- 夏令时切换
- 通知权限被关闭后再开启
- Android 精确闹钟权限被撤回后重新授权

## 24.1 实现说明

三层机制各管一段，任何一层都不能替代另一层：

- **`setAlarmClock`（最近一次提醒）**：Doze 下唯一不被合并延后的注册方式，因此「全库最早的那一条待触发事件」享受此优先级，其余用 `setExactAndAllowWhileIdle`。代价是状态栏出现闹钟图标，需在设置页提供总开关。权限被撤回时退回时间窗口注册，不借 `setAlarmClock` 绕过授权。
- **看门狗闹钟（每 6 小时，`setAndAllowWhileIdle`）**：App 长期不打开时，物化窗口会耗尽，看门狗是唯一还能推进前沿、补发逾期、清理诊断记录的通道。它不发通知、不进系统闹钟列表、不显示图标。用户「强行停止」应用会同时清掉闹钟与广播注册，此时不存在任何自愈通道——这是平台限制，只能在 UI 上说明，不能假装能解决。
- **逾期补发（宽限期默认 24 小时）**：闹钟被 ROM 冻结、关机跨过时刻、注册失败等场景下，事件不得被静默判定过期。已确认逾期的事件写入标记位并排队补发「逾期」通知；超出宽限期才归档为过期。补发必须先于全量重建中的过期判定执行。

硬约束：**每一次注册失败都必须在 `scheduler_health` 留下一行记录**。没有留痕的失败无法按机型定位，"到点什么都没发生"就永远是一句无从查证的抱怨。设置页的「提醒自检」只报系统真正提供的读数；自启动与厂商后台管控没有公开读取接口，一律标注"无法自动检测"，绝不用"已就绪"骗用户。

# 25. 时区与时间规则

时间必须在数据层明确保存“时间语义”。

建议：

- 一次性提醒保存完整日期时间 + 时区信息。
- 重复提醒保存“规则时间” + 时区策略。
- 不要简单把所有重复时间转换成 UTC 时间后永久保存。

### 推荐基线

重复提醒默认理解为：

> “按照用户当前设定的本地时间规则执行”。

例如：

```text
每天 09:00
```

用户跨时区旅行后，默认仍理解为当地每天 09:00。

这个规则需要在产品说明中明确，并在技术设计中统一实现。

# 32. 产品必须避免的错误承诺

不能对用户承诺：

> “任何情况下都 100% 精确到秒响起。”

# 34. 第一版的核心验收标准

一个提醒功能只有同时满足下面条件，才算核心功能完成：

### 创建

用户能够创建一条带文字内容的备忘录，并设置一次性或重复提醒。

### 多提醒

一条备忘录可以同时存在多个提醒规则。

### 后台/关闭

App 不在前台时，系统仍可以触发本地提醒。

### 内容预览

通知可以展示用户设置的提醒正文；关闭正文预览时则不展示完整内容。

### 处理

用户可以从通知/应用内完成提醒或稍后提醒。

### 重复

各种已定义的重复规则能稳定计算下一次时间。

### 历史

每次提醒都有独立事件记录，并可以看到完成与完成时间。

### 修改

修改规则不会留下旧通知。

### 删除

删除后未来通知必须全部取消；恢复后必须重新调度。

### 系统恢复

设备重启、App 再次打开或权限恢复后，可以根据数据库重新建立必要提醒。

# 36. 最终产品基线总结

本产品第一版的核心范围可以浓缩为：

> **一个本地优先的移动端备忘录 + 多规则提醒系统。**

用户可以：

- 创建文字、图片、文件、语音组成的备忘录；
- 可选标题；
- 设置高/中/低优先级；
- 将备忘录放入一个分类；
- 一条备忘录创建多个独立提醒规则；
- 设置一次性和多种重复规则；
- 时间设置支持到秒；
- 到时间后通过系统通知、锁屏、横幅、通知中心/通知栏、声音和角标提醒；
- 每条备忘录决定通知中是否展示正文；
- 通知支持完成和稍后提醒；
- 未完成时可自动重复提醒；
- 重复提醒支持跳过某一次；
- 重复规则支持结束日期；
- 每月不存在日期时自动按当月最后一天处理；
- 完成后的备忘录从当前列表移走，并进入历史；
- 历史保存每一次提醒事件、完成状态和完成时间；
- 删除进入回收站，用户可手动恢复或永久删除；
- 系统通知由操作系统负责执行，App 不依赖持续后台运行；
- MVP 不强制登录、不依赖服务器、不做云同步，但数据模型预留未来同步能力。

# 38. 开发前的关键结论

在开始编码之前，团队应把以下内容视为“不可随意改动”的核心业务规则：

1. **Note、ReminderRule、ReminderOccurrence 必须分离。**
2. **一条 Note 支持多个提醒规则。**
3. **Snooze 只影响当前提醒事件，不改变长期重复规则。**
4. **Skip 只影响当前一次，不影响后续重复。**
5. **完成一次和结束整个重复系列是两个不同动作。**
6. **系统通知只是执行层，本地数据库才是真实数据源。**
7. **修改提醒必须先取消旧调度，再注册新调度。**
8. **删除必须取消未来通知，恢复必须重新调度。**
9. **时间、时区、夏令时、闰年和月底边界必须作为一级测试对象。**
10. **产品不能承诺操作系统环境下绝对“零延迟、零误差”的通知到达。**
